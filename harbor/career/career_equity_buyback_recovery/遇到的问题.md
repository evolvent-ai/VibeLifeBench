# 虚拟时钟时区不一致：问题复盘

本次排查与修复的记录。按「缺陷类型」抽象，便于在其他 task 上复用判据。

---

## 一、根因：**标签与真值不符**（不是"时区不统一"）

时间戳被**按 Asia/Shanghai 挂钟写出，却打上 `Z`（UTC）后缀**。
`2026-06-08T10:00:00Z` 字面意思是 UTC 10:00（北京 18:00），作者本意是北京 10:00。
**同一个字符串同时承载了两个互相矛盾的断言**，差 8 小时。

这不是"两种格式并存"那么轻。格式并存只要各自内部一致就能工作；
**标签说谎则任何一次跨形态比较都错，且错得静默**。

### 为什么会静默

三个条件叠加，缺一不可：

1. **SQLite 的 datetime 列是 TEXT**，排序 / 范围过滤走**字节比较**；
2. 偏移字符的字节序是 `'+' (0x2B) < 数字 < 'Z' (0x5A)`，
   于是 `+08:00` 行**恒排在** `Z` 行之前，与真实时刻无关；
3. 全部数据同为一种错误形态时，**内部自洽**——排序看起来是对的。

所以 bug 只在**新旧形态相遇**时现形：世界时钟写入一行真 UTC，
它就会被排到整个种子语料之前/之后的错误位置。种子自查永远查不出来。

### 决定性判据（可移植）

> 对每个 datetime 列取全部值，比较
> `sorted(vals)` 与 `sorted(vals, key=parse_iso)`。
> **两者不等 ⇒ 排序与真实时间不符。**
> 附带检查该列的偏移形态集合 `{'Z'} / {'+08:00'} / ...`，
> **size > 1 ⇒ 混合偏移，必然埋雷。**

比"grep 一下时区"强得多：它直接测**要害不变量**，
而不是测某种拼写是否出现。修完必须复跑到"无一列命中"。

## 二、真正的教训：**修数据会打死引用该数据的判分逻辑**

这是本次最有价值、也最该记住的一条。

我先转换了 `email` seed 与 10 个 `release-*.json`，看上去干净利落。
**但 rubric 里硬编码着这些时间戳的字面量**，数据一动，判分侧就悬空了：

| 位置 | 形态 | 后果 |
|---|---|---|
| `stage_6` / `stage_10` / `stage_16` | `>= "2026-06-17T09:55:00Z"` 等门槛 | release 减 8h、门槛没减 → **恒 False** |
| `stage_17` / `cross_stage` | `== "2026-07-16T08:00:00Z"` 等值比较 | 与 release-008 不再相等 → **恒 False** |

**死权重 19.0 / 总权重 100.0 = 19.0%**（AST 统计：
`s06_no_soft_commit_to_hr` 2.0、`s10_demand_letter_drafted` 3.0、
`s16_no_privacy_leak` 3.5、`s17_*` 5.5、`cross_reconcile_chain` 5.0）。

而且**是静默的**：check 返回 False 与"agent 没做对"完全同形，
不抛异常、不进日志。若不是回头核对，会当成"这个 task 偏难"。

> **抽象判据：改动被判分逻辑引用的数据前，先枚举全部引用点。**
> 数据与 rubric 之间是**隐式契约**，没有类型系统守护。
> 扫描面至少覆盖：`tests/rubrics/`、`tests/test_*`、`steps/*/solution/oracle.py`。
> 正则不能只扫 seed 与 release——**要扫整个 task 树**。

### 门槛的语义必须还原，不能照着数字平移

三个门槛值**恰好等于被回复邮件的注入时间**，
其不变量是「**回复不得早于它所回复的原信**」。

认出这一点，修法才是对的：**门槛跟着 release 同步减 8h**，不变量守恒。
若只按"看起来该是早上"随手填一个数，不变量就废了——
表面绿灯，实则送分或误杀。**先还原语义，再改数字。**

同理，`oracle.py` 把该时间戳**写进 `severance_review.md` 正文**，
而 `stage_17` 会拿正文串与真实 `posted_at` 对拉。
漏改 oracle → 满分解也拿不到分。**34 份 oracle 各 2 处，一处不能漏。**

## 三、注释是错的，而且正是 bug 的策源地

多个 `utils/dates.py` 写着：

```
All seed rows and every world-controller mutation write +08:00;
emitting Z here would sort server-written rows against the seed ...
```

**与事实相反**——种子写的是 `Z`。
注释还配了看似严谨的字节序论证，读起来很有说服力，于是
`now_iso_z()` 被改成 `return _world_now_iso()`（吐 `+08:00`），
**函数名与行为公然矛盾**，还留了句"名字保留以免动调用点"。

> **判据：注释声称的数据形态，必须拿真实数据验证，不能采信。**
> 一条自信、带论证、且解释了"为何反直觉"的注释，
> 恰恰是**最危险**的一类——它会让后来者跳过验证。
> 本次修复同步改正了 6 个 server 的注释与 `notion/SPEC.md`
> （后者还残留"**没有**模拟时钟"的过期表述，而该 server 确实读世界时钟）。

## 四、"统一"不等于"全部推平"

`calendar` 是**故意的双形态**，推平反而是错的：

- `start_dt` / `end_dt` → `+08:00`：用户在邀请上看到的**挂钟时间**，
  且 `to_storage_offset()` 会把每个查询边界归一到同一偏移；
- `created_at` / `updated_at` → 真 UTC `Z`：审计列，与其他 server 对齐。

**两族各自内部一致即可**，跨族本就不比较。

> **判据：先问"这一列跟谁比较"，再决定它的形态。**
> 同一张表里不同列服务于不同不变量，是完全正常的。
> 「统一」的对象是**同一比较域**，不是整个文件。

同理，`instruction.md` 与 `step-release-map.json` 的 `scenario_time`
保留 `+08:00` 也是对的——它们是给 agent 读的本地挂钟，不是存储形态。

## 五、边界与跳过项

- **跨日回卷**：`calendar` 有 6 个 `T00:00:00Z`，减 8h 会退到前一天
  （`2026-06-08T00:00:00Z → 2026-06-07T16:00:00Z`）。正确，但必须先确认
  该列不与任何纯日期列配对，否则两者会自相矛盾。
- **跳过 < 2020 的锚点**：开户时间 `2018-08-01T00:00:00Z` 与同行的
  `opened_at '2018-08-01'`（纯日期）配对，回卷一天就打架。
  **有意保留，非遗漏。**
- **毫秒形态**：`notion` 全部是 `.000Z`，转换必须保留毫秒段，
  否则 142 行形态漂移。
- **`today_utc()` 的安全性**：全部 34 步的 `scenario_time` 落在本地
  08:00–15:00，故 UTC 日期恒等于本地日期，无跨日歧义。
  **这是需要实测确认的前提，不是可以假设的。**

## 六、工程事故：本地 `pytest.py` 遮蔽真 pytest

task 根目录有个 `pytest.py`（无 pytest 包时的 unittest 兜底），
在该目录下跑 `python3 -m pytest` 会**导入它而非真 pytest**，
报 `ImportError: Start directory is not importable`。

看着像"测试文件坏了"，实则是 import 遮蔽。
**换到 `/tmp` 用绝对路径跑**即可。

> **判据：报错荒谬时先怀疑判据本身，而不是被测对象。**

另：跑测试务必带 `PYTHONDONTWRITEBYTECODE=1` 并事后清理 `__pycache__`
——`.pyc` 会被算进 task checksum，污染门禁新鲜度。
